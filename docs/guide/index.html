Headroom guide

Headroom is a menu bar app for macOS 14 and later. It reports freely and changes nothing until you review and confirm. This guide covers installing it, every part of the app, and the rules it follows.

This guide describes Headroom v0.1.0, the latest release. See what's new; guides for older versions are in the docs/ folder of each release tag.

Install

Headroom runs on macOS 14 or later, on Apple silicon and Intel Macs. There are two ways to get it.

Download

  1. Download Headroom.zip from the latest release.
  2. Unzip it and move Headroom to your Applications folder.
  3. Open it and follow First launch of a download once.

Headroom doesn't update itself (it makes no network calls). Check the releases page for new versions.

Build from source

You need Xcode 16 or later (for Swift 6). There are no other dependencies.

git clone https://github.com/medaimane/headroom.git
cd headroom
make app                  # builds build/Headroom.app (release, signed to run locally)
open build/Headroom.app
make install              # optional: copies the app to ~/Applications

A build you make yourself runs on your Mac without any Gatekeeper prompt.

CommandWhat it does
make appRelease build of build/Headroom.app.
make debug-appDebug build. Clean-ups are always a dry run on your real home folder.
make testRuns the unit tests. Clean-up tests only touch fixture folders in $TMPDIR.
make cli ARGS=storageRuns a read-only command-line report.
make installCopies the app to ~/Applications.
make releaseUniversal, ad-hoc signed build/Headroom.zip and its SHA-256, for a GitHub release.
make iconRe-renders the app icon from docs/assets/icon.svg.
make siteServes this website locally at http://localhost:8765.

First launch of a download

The downloaded app is signed, but not notarized by Apple: notarization needs a paid Apple Developer account, which this project doesn't have yet. macOS therefore asks you to approve Headroom once.

  1. Open Headroom. macOS says it can't verify that the app is free of malware. Click Done (not Move to Trash).
  2. Open System Settings ▸ Privacy & Security and scroll to Security. Next to "Headroom was blocked to protect your Mac", click Open Anyway.
  3. Confirm with your password or Touch ID, then click Open Anyway once more.

After that, Headroom opens normally.

Only approve a copy you trust. Download it from this site or the GitHub releases page, and if you like, compare its checksum with the one in the release notes: shasum -a 256 ~/Downloads/Headroom.zip. The source is open, so you can also build it yourself instead.

First run

  1. Open Headroom. It has no Dock icon; look for the bars icon in the menu bar. On a crowded menu bar it can hide behind the notch.
  2. Click it for the quick view, then Open Headroom for the full window.
  3. Go to Storage. The first visit scans your developer caches; Rescan refreshes them.
  4. Pick some caches and click Review clean-up…. Dry run is on, so the first run only simulates.
  5. When you trust what you see, turn off dry run in Settings ▸ Clean-up. Every clean-up still needs your confirmation.

Menu bar

The menu bar icon shows the overall state. It turns into a warning when disk, memory pressure, swap or temperature needs attention, and it shows free disk space when disk is the problem. The quick view has free disk, memory pressure, swap, CPU and thermal state, plus the groups using the most memory.

Health

Headroom samples the system every 5 seconds (you can change this) and keeps an hour of charts.

  • Memory pressure is the signal macOS itself uses. "Used memory" alone is misleading, because macOS fills spare memory with caches on purpose.
  • Swap growing while you work means memory is short: something is being pushed to disk.
  • Thermal state shows when the Mac is slowing itself down to cool off.
  • Disk free is shown with and without purgeable space.

Grouped processes

Processes are grouped by what you're running: iOS Simulator, Android emulator, Claude Code agents, the Claude app, Metro, Next.js, builds and tests (Nx, Jest, TypeScript, ESLint, Playwright…), other Node, Watchman, Gradle, Xcode, IDEs, Docker and VMs, browsers, and system. Agents, Metro and Next.js are split by project folder, so each worktree gets its own row.

To recognise Metro or Next.js, Headroom looks at a process's command line. It's used only for that and is never stored or shown. Some system processes can't be read without admin rights; Headroom counts them instead of asking for a password.

Storage and clean-up

The Storage page shows free space against your target (100 GB by default) and the size of every location in the cache catalog. Locations marked info only (Trash, Logs, all app caches, Claude Code data) are shown so you know where space goes, but Headroom never cleans them.

How a clean-up works

  1. Pick one or more caches.
  2. Review: Headroom builds a plan that lists each folder, its size and how it rebuilds. Caches whose tool is running are skipped with the reason (for example DerivedData while xcodebuild runs, or Metro's cache while Metro runs).
  3. Confirm: each target is checked again right before it's removed. Anything that changed in between is skipped.
  4. Record: the result goes into History with how to undo it.

Cache clean-ups can't be undone, but the tools rebuild them. The cost is time: the next Xcode build is a full build, the next Gradle or npm install downloads again, and so on. The review screen says exactly what to expect.

Docker

If Docker is installed and running, Headroom shows images, containers, volumes and build cache with what's reclaimable. Docker data is shown only; clean it with Docker's own tools.

Simulators and devices

These are bigger than caches and not rebuilt for you, so each one is removed only after its own confirmation.

ItemHow it's removedHow to get it back
Simulator runtimexcrun simctl runtime deleteDownload it again in Xcode ▸ Settings ▸ Components.
Simulator devicexcrun simctl delete, including its apps and dataCreate it again in Xcode ▸ Devices and Simulators.
Android AVDMoved to the Trash (the .avd folder and its .ini)Put it back from the Trash.
Android system imageMoved to the TrashPut it back, or reinstall in Android Studio ▸ SDK Manager.
Xcode archiveMoved to the TrashPut it back. Archives hold the dSYMs for crash reports of shipped builds.

A running simulator can't be deleted, and AVDs can't be removed while an Android emulator runs. Simulator devices whose runtime is missing are flagged, because they can't boot anyway. AVD settings files are never opened; AVDs are listed by folder name and size.

Explore disk

A read-only, size-sorted drill-down of your home folder. Use it to find what the catalog doesn't cover. Explore never deletes anything; use Show in Finder if you decide to act on something yourself.

Worktrees

Headroom finds every git repository under the folders you choose (~/Developer by default) and lists each worktree with:

  • branch, upstream and last commit date,
  • the number of uncommitted changes (file names are never kept),
  • commits not on any remote branch,
  • node_modules and Nx cache size, filled in after the git pass.

Git runs with --no-optional-locks and never fetches, commits or changes branches, so push status is as of your last fetch. The page is read-only: it shows the facts and you decide what to do with old worktrees.

Workload snapshots

Name a workload (for example "1 sim + 1 emu + Metro + Next + 2 agents"), click Start recording, work as usual, then Stop and save. Headroom keeps the peaks: memory used, worst memory pressure, swap growth, CPU, thermal state, and how many devices and agent sessions were running. Over time this tells you what your Mac can carry before it starts swapping.

History

Every action, including dry runs, is recorded with when it ran, what it touched, its size, whether it worked and how to undo it. Export the history as Markdown from the History page.

Command line

headroom-cli prints the same reports as the app. It's read-only: even plan is a dry run.

swift run headroom-cli health       # memory, swap, CPU, thermal state, disk
swift run headroom-cli processes    # memory and CPU grouped by what's running
swift run headroom-cli storage      # sizes of the known cache locations
swift run headroom-cli devices      # runtimes, simulators, AVDs, system images, archives
swift run headroom-cli worktrees    # branch and push status of every worktree
swift run headroom-cli plan npm.cache gradle.caches   # what a clean-up would remove

Cache ids for plan are listed in the cache catalog. With no ids, plan covers every cleanable cache.

Safety model

These rules are enforced in code (PathGuard, the planner and the executors) and covered by tests.

  • Nothing is deleted without your click, and nothing is deleted automatically.
  • Allow-list only. A target must be strictly inside a catalog folder. Paths with .. are rejected, and a catalog folder that is itself a symlink pointing elsewhere is refused. Symlinks inside are removed as links, never followed.
  • Checked twice: when the plan is made and again right before each removal.
  • Your work is protected. Nothing inside a git working tree, nothing named .env*.local, and no folder that contains one.
  • Running tools win. A cache is skipped while the tool that uses it is running.
  • Per-item confirmation for simulators, AVDs, system images and archives. Docker data is shown only.
  • Repositories are read-only.
  • Processes are never stopped. Headroom reports on agents, simulators, emulators and dev servers; it doesn't quit them.
  • Security settings are never touched: SIP, Gatekeeper, FileVault, the firewall, XProtect and updates. There's no hidden sudo.
  • Debug builds can't delete on your Mac. They force dry run unless pointed at a fixture home in a temporary folder with HEADROOM_HOME.

Permissions and privacy

  • Full Disk Access is optional. Without it, a few protected folders (the Trash, other apps' data) show partial sizes, marked with a lock. Developer caches don't need it.
  • Notifications are requested the first time a warning fires.
  • Open at login stays off until you turn it on.
  • The app isn't sandboxed, because it reads ~/Library/Developer, inspects processes and runs xcrun simctl and git. The hardened runtime is on.
  • No network calls and no telemetry. Logs, env files and configs are never opened; logs are shown by size and location only, because they can contain private data.

Headroom keeps its own data in ~/Library/Application Support/Headroom: settings.json, history.jsonl and snapshots.json.

Uninstall

  1. If you turned on Open at login, turn it off in Settings.
  2. Quit Headroom from its menu.
  3. Move Headroom.app to the Trash.
  4. Optionally, remove ~/Library/Application Support/Headroom to delete its settings, history and snapshots.

FAQ

Why do sizes differ from Finder?

Headroom reports the space files actually take on disk (allocated size), which is what you get back when they're removed. Finder sometimes shows logical size, and APFS clones and purgeable space make the two differ.

Why is my memory "used" so high when pressure is normal?

macOS uses spare memory for caches and compression on purpose. Pressure and swap growth are the signs of a real shortage.

Will it ever clean something by itself?

No. There are no automatic or scheduled deletions. Warnings tell you; you decide.

Why does macOS warn me when I open the download?

Apple only skips that warning for apps notarized with a paid Developer ID. Headroom isn't yet, so you approve it once in Privacy & Security. See First launch of a download.

Why isn't it on the Mac App Store?

The App Store requires the sandbox, which would block reading developer folders and running simctl and git.

A worktree says "unpushed" but I pushed it.

Headroom never fetches. Run git fetch in that repository and scan again.

Contributing

Contributions are welcome. Read CONTRIBUTING.md for setup, the safety rules every change keeps, and how to send a pull request, and report security or safety problems privately as described in SECURITY.md.

The code is a Swift package with no dependencies:

Sources/HeadroomCore     # logic, no UI: metrics, processes, catalog, guard, planner, git, records
Sources/Headroom         # SwiftUI app: menu bar, window, settings
Sources/headroom-cli     # read-only reports
Tests/HeadroomCoreTests  # Swift Testing; clean-ups run only against fixtures in $TMPDIR
docs/                    # this website (GitHub Pages) and its assets

New cache locations go in StorageCatalog.swift with a rebuild note and the processes that should block cleaning. Please add a test for any new rule. Never run live clean-ups on your own Mac while developing; use a fixture home or dry run.

Releasing

The website is published from main and always describes the latest release, so docs for a new feature land together with the release that ships it.

  1. Set the new version in Resources/Info.plist (CFBundleShortVersionString).
  2. Move the Unreleased notes in CHANGELOG.md under the new version and date.
  3. Update the version label on the site (data-version in docs/index.html and docs/guide/index.html) and any docs for the new features.
  4. Run make test and make release. The release script stops if the site or changelog don't match the version.
  5. Commit, create a signed tag vX.Y.Z, push both, then create the GitHub release and attach build/Headroom.zip, keeping that exact file name.
